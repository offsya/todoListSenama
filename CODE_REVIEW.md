### Docker и CI

**1. MongoDB смотрела в сеть без пароля.** Официальный образ `mongo` слушает все интерфейсы и включает авторизацию, только если заданы `MONGO_INITDB_ROOT_*`. Строка `'27017:27017'` в compose открывала базу всем в той же сети: VPS, офисный LAN, кафе. Через `mongosh` можно было читать и править пользователей и задачи в обход API, а заодно и требования «чужие задачи недоступны». На Linux правила iptables от Docker к тому же обходят ufw.
Теперь порт привязан к `127.0.0.1`: он нужен только для `npm run dev` и Compass на этой же машине, а API ходит в базу по внутренней сети Compose. Пароль сознательно не включал: для локального стенда это лишняя сложность, а в реальном деплое база всё равно была бы управляемой и с учётными данными.

**2. Обход лимита попыток входа.** API за nginx работает с `TRUST_PROXY=1`, то есть верит последнему адресу в `X-Forwarded-For`. Но порт 4000 был опубликован и у самого контейнера API, и клиент, пришедший туда напрямую, сам выбирал себе IP. Проверил: при лимите 2 десять попыток входа с разными заголовками дали десять ответов 401 и ни одного 429. Это неограниченный перебор паролей и неограниченные регистрации, а каждая стоит 32 МиБ памяти на scrypt.
Теперь у контейнера API нет опубликованных портов. Порт 4000 (он нужен мобильному приложению на телефоне) обслуживает nginx из образа `web`, конфиг `docker/nginx/api-gateway.conf`. nginx сам дописывает реальный адрес клиента, а подделанные значения левее этого адреса Express игнорирует.

**4. Docker-стек нигде не проверялся.** Ошибка в Dockerfile или в конфиге nginx всплыла бы только у того, кто запустит стек. В CI появилась задача «Docker stack»: она собирает образы, ждёт, пока все контейнеры станут healthy (для nginx-образов добавил healthcheck), и прогоняет `scripts/smoke-test.mjs`. Скрипт работает и локально как `npm run smoke`. Он проверяет обе страницы и их заголовки безопасности, прокси `/api`, вход, 401 без токена, 400 на невалидные данные и 404 на чужую задачу при чтении, изменении и удалении.

**8. CSP.** Токен в вебе лежит в `localStorage` (компромисс описан в README), поэтому единственная защита — отсутствие XSS. В nginx-образах теперь есть Content-Security-Policy, `X-Frame-Options: DENY` и `server_tokens off`. Для веба политика строгая: сборка Vite не содержит ни инлайн-скриптов, ни инлайн-стилей. Веб-сборке Expo нужен `'unsafe-inline'` для стилей: в её `index.html` есть инлайн-сброс стилей, а react-native-web и expo-font добавляют `<style>` во время работы. Скрипты и там ограничены своим origin. zod при первой валидации пробует `new Function` и под CSP пишет в консоль нарушение, поэтому в обоих клиентах он переведён в режим `jitless`. В браузере проверил: внедрённый инлайн-скрипт блокируется, а формы, шрифты иконок и стили работают без единого нарушения.

**19, 20, 23 — мелочи.**

- `npm ci --omit=dev` оставлял пакеты, которые в lock-файле значатся ещё и как опциональные зависимости инструментов: TypeScript, бинарники lightningcss. С `--omit=optional` `node_modules` в образе API занимает 38 МБ вместо 71. Отдельно проверил, что API с этим набором зависимостей запускается.
- jsdom и vitest требуют Node `^22.22.2 || ^24.15.0 || >=26`, поэтому `engines`, README и комментарий в CI поправлены.
- Без `.env` с `JWT_SECRET` стек не запускался. Падала даже команда `docker compose up -d mongo`: Compose подставляет переменные во весь файл сразу. Сначала я оставил это ради понятной ошибки при старте. Но для человека, которому просто прислали ссылку, это лишний барьер. Вдобавок переменные в опубликованном compose-файле заставляют Compose задавать вопрос перед запуском. Теперь, если `JWT_SECRET` не задан, контейнер API при первом старте генерирует случайный секрет (`docker/api-entrypoint.sh`) и хранит его в volume `api-data`. У каждой установки секрет свой, токены переживают перезапуски и обновление образа, а явный `JWT_SECRET` по-прежнему главнее. Проверил на чистой установке: стек поднимается без `.env` и без единого вопроса, и smoke-тест проходит 9 из 9.

### API

**3. Размер списка ничем не ограничен.** `GET /todos` отдаёт весь список одним ответом, а создавать задачи можно было без ограничений, примерно 280 в секунду с одного токена. Замер на 100 тыс. задач: один запрос списка шёл 1,8 с, возвращал 64 МБ и на 0,87 с блокировал event loop для всех пользователей. Зарегистрироваться может кто угодно, так что это готовый способ положить сервер.
Исправлено в коммите «fix(api): cap todos per user and rate-limit /todos per account». У пользователя может быть не больше 1000 задач, сверх лимита — 409 с понятным сообщением. На `/todos` действует лимит 300 запросов в минуту на аккаунт (`TODOS_RATE_LIMIT_MAX`), а не на IP, и считается он после проверки токена. Проверка лимита сделана как «посчитать, потом вставить» и не атомарна. Параллельными запросами его можно превысить на несколько задач, но rate limit ограничивает перебор. Точный счётчик, который пришлось бы синхронизировать при удалениях, здесь не окупается. Пагинацию не добавлял: при 1000 задачах ответ занимает сотни килобайт.

**18.** Тест на некорректный id был только для `GET /todos/:id`. Если убрать `parseParams` из обработчиков `PUT` или `DELETE`, Mongoose бросает `CastError` и клиент получает 500, а тесты бы этого не заметили. Теперь один `it.each` проверяет все три метода.

**22. Токен удалённого пользователя.** `/auth/me` проверяет, что пользователь существует, а `/todos` доверяет подписи токена. Если удалить пользователя из базы, его токен до истечения срока сможет создавать задачи без владельца. Эндпоинта удаления пользователей нет, поэтому сейчас это теоретический сценарий. Я записал его в README рядом с отсутствием отзыва токенов: и то и другое решается одним механизмом.

**21.** Сервер отвечает 415 на неподдерживаемые `Content-Encoding` или кодировку тела, и на это есть тест, а в таблице ошибок README этой строки не было. Добавил.

### Общий клиент (`packages/shared`, `packages/client`)

**9. Запоздавший 401.** Любой ответ 401 на запрос с токеном сбрасывал текущую сессию. Сценарий: пользователь снова вошёл в соседней вкладке, пока старый запрос со старым токеном ещё шёл. Ответ 401 разлогинивал новую сессию и стирал её из `localStorage`, то есть во всех вкладках. Теперь API-клиент передаёт в `onUnauthorized` токен, который отклонил сервер, а хранилище сессии (`invalidate`) выходит, только если этот токен всё ещё текущий.

**10. Задача уходила в чужой список.** TanStack Query вызывает колбэки ещё не завершённой мутации с опциями последнего рендера. Если аккаунт сменился до ответа на `POST /todos`, `onSuccess` записывал задачу Алисы в кеш Боба, и она так там и оставалась. Теперь мутации в `onMutate` фиксируют кеш пользователя, который их начал, и работают только с ним. Ошибки запросов предыдущего пользователя новому не показываются. Оба сценария (9 и 10) воспроизведены тестами.

**11. Таймаут.** Таймер сбрасывался сразу после получения заголовков, а чтение тела ничем не ограничивалось. Если связь обрывалась посреди ответа, спиннер крутился вечно, и ошибка `TIMEOUT` не возникала. Теперь таймаут покрывает весь запрос, включая тело.

Последние два исправления (9 и 10) — коммит «fix(client): ignore responses that belong to a previous session», таймаут — «fix(shared): apply the request timeout to reading the body».

### Веб

**5. Кольцо фокуса.** Фокус показывался тенью с прозрачностью 35–40%. Контраст получался 1,76:1 на светлой теме и 1,85:1 на тёмной при требуемых WCAG 3:1. В Windows High Contrast тени отключаются, и индикатор фокуса пропадал совсем. Теперь это сплошной `outline` толщиной 2 px цвета `--color-primary`: 6,3:1 на светлой теме и 5,0:1 на тёмной.

**6. Потеря фокуса.** Под фильтром «Active» отметка задачи выполненной оптимистично убирала строку, и фокус падал на `<body>`. Пользователю клавиатуры или скринридера приходилось начинать с начала страницы, причём на основном действии приложения. Для удаления это уже было решено, для переключения статуса — нет. Теперь фокус переходит на соседнюю задачу. После входа фокус тоже оставался на `<body>`, теперь он ставится в поле новой задачи. Проверил и тестом, и руками в браузере.

**12. Тесты валидации.** Фейковый API в тестах отвечает той же ошибкой zod, что и форма, поэтому тесты «не добавлять пустую задачу» и «не сохранять пустой текст» проходили и с отключённой валидацией. Теперь они ещё проверяют, что запрос `POST` или `PUT` не ушёл, а редактор остался открытым.

Коммит — «fix(web): visible focus ring and focus that survives list changes».

### Мобильное приложение

**7. Клавиатура на Android.** В комментариях было написано, что Android сам ужимает окно под клавиатуру. С SDK 57 это не так: приложение рисуется edge-to-edge, и в этом режиме `adjustResize` окно больше не ужимает. На экране регистрации клавиатура закрывала поле подтверждения пароля, сообщение об ошибке и кнопку, а прокрутить было нечего, потому что контент помещался на экран. То же происходило при редактировании задачи в нижней половине списка. Экраны с полями ввода теперь обёрнуты в `KeyboardAvoidingView` с отступом на высоту нативного заголовка. На iOS ничего не изменилось: там отступ под клавиатуру по-прежнему делает `ScrollView`. **На реальном устройстве и эмуляторе я это не проверял**: исправление сделано по исходникам React Native и документации Expo. Это первое, что стоит прогнать на Android перед релизом.

**13–14. Веб-сборка мобильного приложения.** Она входит в Docker-стек, поэтому её поведение тоже важно.

- react-native-web 0.21 не знает `submitBehavior` и читает только `blurOnSubmit`. Enter в редакторе с пустым текстом закрывал его и молча выбрасывал правку вместо сообщения «Text must not be empty». После добавления задачи фокус уходил на `<body>`. Теперь задан и `blurOnSubmit={false}`; на iOS и Android `submitBehavior` по-прежнему главнее.
- Пробел не переключал чекбокс задачи: react-native-web обрабатывает пробел только для `role="button"`. Добавил обработчик.
- Выход в одной вкладке не доходил до других: в отличие от веба, здесь не было слушателя `storage`. Добавил.

Всё это проверил в браузере на production-экспорте.

**15–17.**

- Относительный адрес API (`/api`, как в Docker) теперь разрешён только на вебе. Если по ошибке положить его в `apps/mobile/.env`, сборка для устройства сразу падает с понятным сообщением, а не выдаёт «Unable to reach the server» на каждом запросе.
- Добавлен маршрут `+not-found` со ссылкой на список, вместо служебного экрана Expo Router с картой сайта.
- Новые тесты:
  - регистрация: проверка совпадения паролей и то, что на сервер уходят только email и пароль (лишнее поле API отклонил бы с 400);
  - переименование задачи с экрана списка;
  - неизвестная ссылка;
  - холодный старт: пока keychain не ответил, ничего не рисуется и splash не скрывается.

Коммит — «fix(mobile): keyboard on Android, web build behaviour, missing tests».

## Что понравилось

Ревью — это не только список недостатков, поэтому отмечу и то, что сделано хорошо и что я перепроверил отдельно:

- **Изоляция данных**: все запросы к задачам фильтруются по `{ _id, owner }`. Чужая и несуществующая задача дают одинаковые 404, а владельца нельзя подменить через API: строгие схемы отклоняют лишние поля.
- **JWT**: алгоритм HS256 зафиксирован и при подписи, и при проверке. Токены с `alg: none`, HS512, чужим секретом, истёкшим сроком или без `sub` отклоняются.
- **Входные данные**: zod и `sanitizeFilter`. Операторы MongoDB, `__proto__`, массивы, `null`, глубокая вложенность, битый gzip и неверная кодировка дают 4xx, а ответы 500 ничего не раскрывают.
- **Вход**: время ответа выровнено фиктивным хешем, scrypt считается в пуле потоков, а гонка параллельных регистраций реально доходит до ветки duplicate key и проверена тестом.
- **Тесты API**: они проверяют, что данные не изменились, а не только статус ответа. Каждый тестовый файл работает в своей базе, поэтому файлы гоняются параллельно.
- **Клиенты**:
  - кеш разделён по пользователям;
  - откат оптимистичных правок затрагивает только изменённые поля;
  - хранилище сессии не даёт медленному чтению затереть более новую сессию;
  - guards ничего не делают, пока сессия загружается;
  - параметр `from` после входа принимается только как внутренний путь, так что открытого редиректа нет.

## Что оставил как есть

Это не забытые проблемы, а решения. Все они описаны в README, в разделе об ограничениях:

- **Нет refresh-токенов и отзыва токенов на сервере**: выход только локальный, токен живёт до истечения (по умолчанию 7 дней). Сюда же относится пункт 22.
- **Регистрация отвечает 409 на занятый email** и тем самым раскрывает, что адрес зарегистрирован. Без подтверждения почты это честнее, чем делать вид, что регистрация прошла.
- **Лимит в 1000 задач не атомарный** (см. пункт 3), счётчики rate limit хранятся в памяти одного процесса. Для нескольких экземпляров API нужен Redis.
- **MongoDB в Docker без пароля**, но доступна только с этой машины.
- **CSP веб-сборки Expo разрешает инлайн-стили**: без этого не работает react-native-web.
- **Интерфейс только на английском.** Уязвимости из `npm audit` — в транзитивных зависимостях CLI-инструментов Expo, в API и в собранные приложения они не попадают.
